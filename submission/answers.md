## 1. Xronos timing warm-up (1 pt)

**1.1 Logical time (examples 02/03):**
In Example 02, the printed tags `logical t= 0.0 ms`, `100.0 ms`, `200.0 ms`, `300.0 ms`, `400.0 ms` carry logical timestamps, as do `send t=...` and `receive t=...` in Example 03. They are identifiable as logical rather than wall-clock because they advance in strictly discrete, mathematically exact increments (multiples of 100.0 ms and 250.0 ms) with zero microsecond jitter or system scheduling drift, unlike wall-clock time (`current_time=03:14:22.275018`). Furthermore, under `--fast` execution mode, these logical timestamps remain identical while wall-clock execution finishes in milliseconds.

**1.2 Where the 500 ms delay is configured / where it is visible (example 03):**
The 500 ms delay is configured in `examples/03_logical_delay.py` at line 65: `env.connect(commander.command, actuator.command, delay=timedelta(milliseconds=500))`. It is visible in the console output in the exact 500.0 ms difference between emission and reception tags: command #0 sent at t=0.0 ms arrives at t=500.0 ms, command #1 sent at t=250.0 ms arrives at t=750.0 ms, etc.
*Prediction for 300 ms delay:* The receive lines will shift to `t_sent + 300.0 ms`, producing: `receive t= 300.0 ms command #0 (sent at t=0.0 ms)`, `receive t= 550.0 ms command #1 (sent at t=250.0 ms)`, `receive t= 800.0 ms command #2 (sent at t=500.0 ms)`, `receive t=1050.0 ms command #3 (sent at t=750.0 ms)`, and `receive t=1300.0 ms command #4 (sent at t=1000.0 ms)`. Rerunning with the edit confirmed this prediction exactly. Every arrival lands at exactly `send + delay` without jitter because Xronos implements logical delays as tagged discrete-event queue offsets computed by tag addition, rather than wall-clock sleeps or thread timers subject to OS latency.

**1.3 Lag and slack under an overrunning handler (example 04):**
When `SlowWorker.crunch` runs for ~80 ms against a 50 ms deadline, worker `slack` decreases from +48.51 ms at invocation to -31.53 ms upon completion (`before_deadline=False`), indicating an overrun of ~31.5 ms, while the monitor's `lag` jumps from ~0.2 ms to 31.60 ms at t=200 ms because the worker's synchronous handler blocked the event loop thread. The next monitor tick (t=300 ms) recovers to lag=0.38 ms because the worker only executes every 400 ms, allowing the runtime to rapidly drain the lightweight (<1 ms) monitor handler and catch up with physical time.

**1.4 Retroactive fallback (example 05): peak lag A vs. B; when each
fallback fired relative to the deadline; why A is not enforcement and which
two constructs implement B:**
Peak monitor lag was 1101.1 ms in Phase A (handler lag reached 1201 ms), compared to only 0.6 ms in Phase B. In Phase A, the fallback engaged 800 ms after the deadline moment (at wall-clock t=1401 ms instead of t=600 ms = request 200 ms + deadline 400 ms), whereas Phase B issued its fallback on time at logical t=600.0 ms (lag 0.5 ms, 0 ms late relative to deadline). Phase A is not deadline enforcement because the inference call blocks the reaction handler inline, preventing the event loop from executing any events until the slow handler finishes, so an after-the-fact check cannot protect the physical deadline. Phase B implements an enforceable race using two independently scheduled programmable logical timers (`xronos.ProgrammableTimerDeclaration` for response and deadline) as competing events in the discrete-event queue (with the live coach replacing the response timer with an asynchronous `PhysicalEventDeclaration`).
